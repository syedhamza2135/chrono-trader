## Findings

### E-1 (low; judge said medium, skeptic lowered it). A restart under another library or code version would mix vectors silently

- File: `reader/embed.py:94-103` (`manifest`), `166-175` (`check_manifest`), `183-184` (a part is skipped because its
  file exists), `271-278` (versions recorded at `finish`, not at run time).
- Evidence: each part's manifest holds the vintage, repo, commit, counts and id hashes. It holds no token cap, batch,
  tokenizer, pooling, dtype, torch or transformers version, or code version. So a resume after an upgrade or an edit to
  `embed_ids` keeps the old parts, writes new ones under the new definition, and `check_manifest` passes. The average
  vector depends on the library: in the installed transformers 5.22.0, `utils/output_capturing.py:234` and `296-305`
  replace the last hidden state with the output after the final norm, and ModernBERT takes that path
  (`modeling_modernbert.py:421`, `465`). `tests/test_embed.py:75` computes the average with the same expression as the
  code, so it would not catch a change. `requirements.txt:13-14` pins torch 2.15.0+cpu and transformers 5.22.0, but
  nothing checks that at run time.
- Current table: not affected. `run.log` shows one run and `run.err` one weight load per vintage. The parts were
  written 21 Nov 20:46 to 22 Nov 02:53 New York, and the libraries were installed on 30 Oct. Between `e53c114` and
  `3d1df9b`, `embed.py` only gained the arrays functions.
- Skeptic: confirmed, lowered to low, because the run is finished and every part exists. The real exposure is the M5
  morning job, which reuses `embed_ids` (`reader/embed.py:28-29`) and is not built yet.
- Fix: add the cap, batch, pooling, tokenizer file ids, torch and transformers versions and a hash of `embed_ids` to
  the manifest, and make the M5 job assert them. Belongs in M5's entry requirements.

### C-1 (low; judge said medium, skeptic lowered it). Nobody but the author can check the second probe freeze

- File: `research/audit/cutoff.md:316-321` and `596-600`; `reader/cutoff.py:572-580` (`cmd_probes2`).
- Evidence: the only records that the probe list and the rules were fixed before any score are file times on the
  laptop, the hashes `cmd_probes2` saves at scoring time, and the doc's own words. All the files arrived in one commit,
  `e53c114` (22 Nov 10:32 +0500, which is 00:32 New York), about eight hours after the run. The "16:21" freeze is
  34 seconds after the last write to `cutoff.py` (16:20:51), in the same minute as the run's first file
  (`run_probes2.log` created 16:21:25). `cmd_probes2` checks no freeze, and it refuses only when `scores.parquet`
  exists. `cutoff.md:319` says the section was written before any vintage scored, but 8.9 to 10 were written after.
  The first freeze has a second witness: `probes2_judge.md` (written 16:09:54) records its hashes.
- What speaks for the record: the file times are in order, the log shows one run of 11 vintages, and its hashes equal
  `scores.json` and the committed `probes2.csv`. The skeptic found no sign of an earlier run that was scored and moved
  away (the Recycle Bin holds 2 items, neither a score file).
- Skeptic: confirmed, lowered to low. The local record is coherent, no vintage fails, and no decision rests on the
  freeze. It is a weak record of the process, with a cheap fix for next time.
- Fix: next time, commit the frozen files (or send their hashes to the owner) before scoring, make `cmd_probes2`
  refuse unless the files match that record, and reword `cutoff.md:319` to cover 8.1 to 8.8 only.

### E-2 (low). The tokenizer is never checked against the pins

- File: `reader/cutoff.py:180-183`; `reader/embed.py:204`.
- Evidence: the tokenizer loads from the 2014 vintage's folder, and `cmd_run` never checks that folder. The judge ran
  `download.problems` on it and got an empty list, so it matches today.
- Fix: check the 2014 folder inside `tokenizer()`, or load the tokenizer from the vintage folder just checked.

### E-3 (low). The manifest pins the commit, not the weights hash

- File: `reader/embed.py:100` and `277`.
- Evidence: the weights are checked by SHA-256 at load, and the run stops on a mismatch before any part is written
  (`embed.py:215`). But `embeddings.json` copies `weights_sha256` from the pins at finish time, and `finish` never
  hashes the weights again. All ten manifests match the pins today.
- Fix: put `weights_bytes` and `weights_sha256` in each manifest.

### E-4 (low). The New York year edge is right in code but no test covers it

- File: `reader/vintage.py:15-18`, `reader/embed.py:64-66`; `tests/test_embed.py:40`.
- Evidence: on made-up times the rule is right (2017-01-01 03:00 UTC, which is 31 Dec 2016 in New York, gets the
  2015 vintage). But the real table has 0 rows whose UTC year differs from the New York year, so a slip to UTC years
  would pass every test and check. Such a slip would let the vintage of a year read stories from that year.
- Fix: a test with fixed times at 31 Dec 23:30 and 1 Jan 00:30 New York, and one 2015 story sent to `select`.

### C-2 (low). The recorded `cutoff.py` hash is that of the Windows working copy

- File: `research/audit/cutoff.md:545-546`, `598-599`; `.gitattributes:1-3`.
- Evidence: `sha256sum reader/cutoff.py` gives `8bae55f5...3b3e`, as the doc says. `git show
  3d1df9b:reader/cutoff.py | sha256sum` gives `70045341...36ce`. `core.autocrlf` is true and `.gitattributes` keeps
  only `reader/*.csv` as bytes, so on a checkout without CRLF the doc's hash cannot be reproduced. The checker found
  the same (its one split result in 8.9). The `probes2.csv` hash `eed31d91...d5bd` matches in git and on disk.
- Fix: add the committed hash
  `7004534124287875504bd044498c0d36696d3adbc3ffb3ece99c32b1418336ce` to 8.8 and say which copy each hash is of.

### C-3 (low). `report-probes2` only prints a `cutoff.py` change (P2-7, partly fixed)

- File: `reader/cutoff.py:586-589`.
- Evidence: a changed `probes2.csv` stops the report (586-587). A changed `cutoff.py` is printed side by side and
  the report goes on (588-589). The doc claims no more than that (`cutoff.md:574-576`).
- Fix: stop on a mismatch, comparing bytes with LF line ends so C-2 does not trip it.

### C-4 (low). The reading of q2023c leans on an unchecked fact

- File: `research/audit/cutoff.md:640-643`.
- Evidence: the doc gives a 2023 event "(from memory, not checked)" beside the flag. That goes against the Facts
  rule, and an event in 2023 cannot explain a step in a vintage that ends in 2022. A stronger argument is in the
  numbers and goes unstated: the 2022 vintage shows no knowledge of q2023b (February 2023, score -6.96) but scores
  q2023c (August 2023) like 2023 and 2024 (-3.07 against -3.24 and -3.76). A leak at the training end would reach
  February before August. Also, 1 of the 2022 vintage's 2 informative probes flags.
- Fix: drop the parenthetical or check and cite it; add the February-before-August argument and "1 of 2".

### W-1 (info). The leak check's scramble keeps the sign pattern of late vectors

- File: `eval/leaks.py:66-75`, used at `121-122`.
- Evidence: scramble swaps late vectors and scales them by a positive factor, so the share of positive entries is
  unchanged (0.48203125 before and after, on a made-up frame). A leak that reads such a statistic is still caught by
  shift (over a time window) or delete (over all late rows), so the rule "at least one of three catches it" holds.
- Fix: also flip each late vector's sign at random, as the module does for returns.

### E-5 (info). `manifest.json` is not written atomically

- Fix: write to a temporary name and rename, as `write_atomic` does.

### E-6 (info). A rerun matches within float16 rounding, not bit for bit
